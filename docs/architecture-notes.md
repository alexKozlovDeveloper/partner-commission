## 1. Задача в двух словах

- **Пользователи** идентифицируются по `ExternalId`. У каждого может быть **партнёр** (тот, кто его пригласил) — так получается дерево.
- **События** приходят по пользователю: `EventExternalId` + `Profit` (может быть отрицательным).
- За событие с **положительным** Profit комиссию получают **все партнёры вверх по цепочке** от владельца события:
  уровень 1 — прямой партнёр, уровень 2 — партнёр партнёра и т. д.
- Две схемы (переключаются админом, влияют только на новые расчёты):
  - **Linear**: `L × Profit / 100` → уровень 1 получает 1%, уровень 2 — 2%, …
  - **Fibonacci**: `F(L) × Profit / 100` → 1%, 1%, 2%, 3%, 5%, …
- Каждая комиссия обязана хранить `schema_type`.
- На кошелёк попадают **только комиссии**, не сами события. Выплата накопленного на кошелёк — **периодическая**. Баланс = сумма **выплаченных** комиссий.
- Нефункциональные: микросервисы, горизонтальное масштабирование, отказоустойчивость (retry, circuit breaker, graceful shutdown),
  логи/метрики/health, **гарантия отсутствия двойных начислений**. Допущения задания: можно HTTP + Outbox вместо Kafka,
  фоновые процессы с retry вместо распределённых транзакций, глубину дерева ограничить (например, 10).

## 3. Общая архитектура: три сервиса

```
                         +---------------------------+
   client  ------------> |         Partners          |  users, partner links, tree
                         |  db: partners             |
                         +-------------^-------------+
                                       | GET /internal/users/{id}/ancestors
                                       | (sync HTTP, retry + circuit breaker)
                         +-------------+-------------+
   client  ------------> |        Commissions        |  profit events, commissions,
                         |  db: commissions          |  current schema, outbox
                         +-----+---------------+-----+
                               |               |
        POST /internal/        |               | POST /internal/commissions/payments:query
        commissions (outbox)   |               | (статус выплаты для деталей события)
                               v               v
                         +-----+---------------+-----+
   client  ------------> |          Wallets          |  accrued commissions, periodic payout,
                         |  db: wallets              |  balances, payout history
                         +---------------------------+
```

Правило стрелок: стрелка идёт **от того, кто вызывает, к тому, кого вызывают**.

| Сервис | Отвечает за | Таблицы | Фоновые задачи |
|---|---|---|---|
| **Partners** | пользователи, связи, дерево, правила дерева | `users` | — |
| **Commissions** | приём событий, расчёт, текущая схема, доставка в Wallets | `profit_events`, `commissions`, `settings`, `outbox_messages` | `ProfitEventProcessor`, `OutboxDispatcher` |
| **Wallets** | начисленные комиссии, выплата, баланс, история | `wallet_entries`, `wallets` | `PayoutProcessor` |

### Почему именно так разрезано

- **По владению данными.** Дерево меняется редко и нужно только для «кто над кем». Комиссии — это поток событий и расчёт.
  Кошельки — деньги и выплаты. У каждого своя причина меняться и свой владелец данных.
- **Database per service.** Сервисы не читают чужие таблицы, только API. Иначе это «распределённый монолит»:
  любая миграция одного ломает другого.
- **Флаг «выплачено» живёт в Wallets**, потому что выплату делает Wallets. Commissions спрашивает его при запросе деталей.

### Альтернативы, которые рассматривались

| Вариант | Почему нет |
|---|---|
| Монолит | прямо противоречит требованию «микросервисная архитектура» |
| Два сервиса (Commissions + Wallets вместе) | выплата и баланс — отдельная предметная область с собственным расписанием; разделение показывает границы |
| Отдельный сервис настроек/админки | одна настройка (схема) — не стоит отдельного процесса |
| Отдельный сервис «дерево» и «пользователи» | это одна сущность, разрезать искусственно |
| API Gateway | для тестового не нужен; единообразие путей `/users/{id}/...` уже сделано, gateway можно поставить сверху (роутинг по сегменту `wallet`/`profit-events`) |

## 4. Путь одного события от начала до баланса

Пример: `u1 ← u2 ← u3` (u3 пригласил u2, u2 пригласил u1), схема Linear, событие u3 на 100.

1. **Клиент** → `POST /users/u3/profit-events {"eventExternalId":"evt-1","profit":100}` в Commissions.
2. `CommissionsService.ReceiveProfitEventAsync`:
   - ищет `evt-1` (быстрая проверка на повтор);
   - читает текущую схему из `settings` → `Linear`;
   - вставляет строку в `profit_events`: `Status = Received`, `SchemaType = Linear`, `NextAttemptAtUtc = now`;
   - если параллельно вставили то же самое — ловит unique violation и отвечает как на повтор.
   - Ответ **202 Accepted** + `Location: /users/u3/profit-events/evt-1`. Ничего ещё не посчитано.
3. **ProfitEventProcessor** (каждые 5 с, только на экземпляре-лидере) берёт до 50 событий `Received`/`Unresolved`,
   у которых `NextAttemptAtUtc <= now`, по порядку `CreatedAtUtc`. Для каждого — новый DI-scope и `ProfitEventHandler`.
4. **ProfitEventHandler.HandleAsync**:
   - стартует `Activity "ProcessProfitEvent"` → у всех логов появляется TraceId, он же уйдёт в Partners;
   - загружает событие; если уже не `Received/Unresolved` — пропуск;
   - Profit > 0 → `GET /internal/users/u3/ancestors` в Partners → `[u2 (1), u1 (2)]`;
   - `CommissionCalculator.Calculate(100, Linear, [u2/1, u1/2])` → `u2: 1.0000`, `u1: 2.0000`;
   - в **одной транзакции** (один `SaveChangesAsync`): 2 строки `commissions` + 2 строки `outbox_messages` + событие `Processed`;
   - после коммита — метрики `commissions_accrued_total`, `..._amount_total`.
5. **OutboxDispatcher** (каждые 5 с, лидер) берёт неотправленные сообщения → `OutboxMessageHandler` → `POST /internal/commissions`
   в Wallets с `CommissionAccruedMessage` → при 2xx ставит `ProcessedAtUtc`.
6. **Wallets `ReceiveCommissionAsync`**: вставляет `wallet_entries` (`Pending`, PK = `CommissionId`). Повтор — 204 без изменений.
7. **PayoutProcessor** (каждые 15 с, лидер) → для каждого пользователя с `Pending` → `PayoutHandler`:
   в одной транзакции все его записи → `Paid` + `wallets.Balance += сумма` (кошелёк создаётся при первой выплате).
8. Итог: `GET /users/u1/wallet` → `{"balance":2.0000}`, `u2` → `1.0000`.
   `GET /users/u3/profit-events/evt-1` → комиссии со статусом `Paid` (Commissions спросил у Wallets).

Если переключить схему на Fibonacci и отправить `evt-2` на 100 → `u2: 1.0000`, `u1: 1.0000`, а `evt-1` остаётся `Linear`.

Где что может сломаться и что тогда происходит:

| Сбой | Поведение |
|---|---|
| Partners недоступен | событие остаётся `Received`, `Attempts++`, повтор через 2, 4, 8… до 300 с |
| Пользователя нет в Partners (404) | `Unresolved`, перепроверка раз в 30 с; появится пользователь — обработается |
| Wallets недоступен | outbox копится (`outbox_pending` растёт), детали события показывают `Unknown`; поднимется — всё доставится |
| Сервис упал посреди обработки | транзакция не закоммичена → событие осталось `Received` → обработается снова |
| Упал после отправки в Wallets, но до `ProcessedAtUtc` | сообщение уйдёт повторно, Wallets распознает дубль по `CommissionId` |

## 5. Связь между сервисами

### Синхронный HTTP — для чтения, когда нужен ответ сейчас

- Commissions → Partners: цепочка предков. Нужна прямо во время расчёта.
- Commissions → Wallets: статусы выплат для деталей события.
- Typed HttpClient (`PartnersClient`, `WalletsClient`) + `AddStandardResilienceHandler()` (retry, circuit breaker, timeouts).
- Контракт между сервисами — только `ExternalId`, внутренние `Guid` наружу не уходят.

### Transactional outbox — для доставки Commissions → Wallets

**Проблема, которую решает.** Надо и записать комиссию в свою БД, и сообщить Wallets. Если сначала коммит, потом HTTP —
процесс может упасть между ними, и Wallets никогда не узнает. Если сначала HTTP, потом коммит — Wallets узнает о том,
чего в итоге нет. Распределённой транзакции (2PC) между БД и HTTP нет.

**Как работает.**
1. В той же транзакции, где пишутся комиссии, пишется строка в `outbox_messages` (`Type`, `Payload` JSON, `NextAttemptAtUtc`).
   Либо записалось всё, либо ничего — атомарность даёт сама БД.
2. Отдельная фоновая задача (`OutboxDispatcher`) читает неотправленные строки и отправляет их HTTP-запросом.
3. После успешного ответа ставит `ProcessedAtUtc`. Ошибка → `Attempts++`, `NextAttemptAtUtc = now + backoff`, `LastError`.
4. Упасть можно между «отправил» и «отметил» → сообщение уйдёт ещё раз. Поэтому гарантия **at-least-once**,
   а получатель обязан быть **идемпотентным** (Wallets дедуплицирует по `CommissionId`, это PK).
   At-least-once + идемпотентный получатель = эффективно exactly-once.

**`MessageType` — константа-строка** (`"commission.accrued"`), а не `nameof(класса)`: тип хранится в таблице,
переименование класса не должно ломать уже лежащие сообщения.

**Сериализация**: `JsonSerializer.Serialize/Deserialize` с настройками по умолчанию с обеих сторон outbox —
главное, чтобы писатель и читатель совпадали.

### Почему статус выплаты не «пушится» обратно

Было два варианта:

| Вариант | Плюсы | Минусы |
|---|---|---|
| Wallets после выплаты шлёт в Commissions «выплачено» (второй outbox) | детали события не зависят от Wallets | второй outbox, диспетчер в Wallets, эндпоинт `/paid`, данные дублируются |
| **Commissions спрашивает Wallets при запросе деталей (выбрано)** | один источник правды, меньше кода | детали зависят от доступности Wallets → деградация в `Unknown` |

Выбран pull: проще, нет дублирования. `payments:query` — `POST` с телом (id-шники GUID быстро переполняют URL, ~42 символа на id).

### Альтернативы outbox'у

| Вариант | Комментарий |
|---|---|
| Kafka/RabbitMQ (MassTransit) | стандарт в проде; задание разрешает не делать; всё равно нужен outbox, чтобы атомарно «записать в БД и опубликовать» |
| CDC (Debezium читает WAL) | мощно, но тяжёлая инфраструктура |
| 2PC / распределённые транзакции | задание прямо говорит: вместо них — фоновые процессы с retry |
| Синхронный вызов Wallets внутри обработки события | связывает доступность двух сервисов; при падении Wallets не обработать события |

## 6. Идемпотентность

Главное требование задания — **никаких двойных начислений**. Защита стоит на каждом шаге и **в базе**, а не только в коде.

| Шаг | Ключ-гарантия | Что при повторе |
|---|---|---|
| Создание пользователя | `users.ExternalId` UNIQUE | 200 и id существующего |
| Приём события | `profit_events.EventExternalId` UNIQUE | 200 и текущий статус; другой пользователь / другой Profit → 409 |
| Начисление | `commissions (ProfitEventId, Level)` UNIQUE | второй `SaveChanges` падает, транзакция откатывается |
| Приём в Wallets | `wallet_entries.CommissionId` PRIMARY KEY | 204 без изменений; другие данные → 409 |
| Выплата | advisory lock на задачу + одна транзакция на пользователя | запись уже `Paid` — второй раз не выбирается |
| Назначение партнёра | повтор того же партнёра | 204 «unchanged» |

### Паттерн «проверка → вставка → catch»

Используется в `UsersService.CreateAsync`, `CommissionsService.ReceiveProfitEventAsync`, `WalletsService.ReceiveCommissionAsync`.

```csharp
// 1. проверка — оптимизация: обычный дубль отвечаем быстро и без исключения
var existing = await Find(...);
if (existing is not null) return Duplicate(existing);

// 2. вставка
db.Add(entity);

// 3. уникальный ключ + catch — гарантия
try { await db.SaveChangesAsync(ct); }
catch (DbUpdateException ex) when (ex.IsUniqueViolation())
{
    db.ChangeTracker.Clear();                 // выкинуть неудавшуюся вставку из контекста
    var concurrent = await Find(...);         // прочитать то, что вставил конкурент
    return Duplicate(concurrent);             // сверить данные: совпадают → дубль, нет → 409
}
```

**Почему три части, а не одна.**
- Только проверка (`if exists`) — **гонка check-then-act**: два параллельных запроса оба видят «нет» и оба вставляют.
- Только catch — работает, но каждый обычный дубль превращается в исключение (дорого, шумно в логах).
- Проверка — оптимизация, **ограничение в БД + catch — гарантия**. Что бы ни случилось с таймингами, второй не пройдёт.

`IsUniqueViolation()` (Shared/Data) = `ex.InnerException is PostgresException { SqlState: "23505" }`. PK нарушается с тем же кодом.

**Почему не `SELECT ... FOR UPDATE` / serializable.** Блокировать нечего — строки ещё нет. Serializable дал бы ошибку `40001`
и повтор всей операции — сложнее, а уникальный индекс решает то же самое проще.

**Повтор с другими данными — 409, а не тихий успех.** Одинаковый id с разным содержимым = ошибка отправителя.
Молча принять — потерять данные или начислить не то.

**Внимание, известное ограничение**: Profit хранится `numeric(18,4)`. Если прислать `0.123456`, база сохранит `0.1235`,
а повтор того же запроса сравнит `0.1235 != 0.123456` → 409 вместо 200. Лечится округлением при приёме
(`Math.Round(profit, 4, AwayFromZero)`), в итоговой версии решено не делать (см. раздел 22).

## 7. Фоновая обработка: таблица как очередь

### Почему события обрабатываются в фоне, а не в запросе

- Расчёт требует похода в Partners. Если Partners лежит — синхронный приём отвечал бы ошибкой, клиенту пришлось бы повторять.
- Приём должен быть **быстрым и почти всегда успешным**: записал строку — ответил 202. Обработка может ломаться и повторяться сколько угодно.
- База одновременно и очередь, и источник правды: ничего не теряется при рестарте.

### Базовый класс `PollingBackgroundService<TDbContext>` (Shared/Hosting)

Все три задачи (`ProfitEventProcessor`, `OutboxDispatcher`, `PayoutProcessor`) наследуются от него. Он делает:

```
ExecuteAsync:
  timer = PeriodicTimer(Options.PollInterval)
  do {
     try  { RunWithLockAsync }
     catch OperationCanceled при остановке → выйти
     catch Exception → LogError("{Job} tick failed"), продолжить
  } while (await timer.WaitForNextTickAsync)

RunWithLockAsync:
  новый scope → DbContext → AdvisoryLock.TryAcquireAsync(LockKey)
  не взяли → LogDebug("... skipping tick"), выход
  взяли → RunOnceAsync (реализует наследник) → lock снимается в DisposeAsync
```

Наследник задаёт только `LockKey` и `RunOnceAsync`. Интервал и размер пачки — из конфига (`BackgroundJobs:{ИмяКласса}`), см. раздел 18.

- **`PeriodicTimer`** (.NET 6+) — простой асинхронный таймер; `WaitForNextTickAsync` завершается при остановке → цикл выходит сам.
- **`do/while`** — первый тик сразу при старте, не через интервал.
- **Исключение в тике не валит сервис.** В .NET 8 необработанное исключение в `BackgroundService` по умолчанию останавливает хост —
  поэтому общий catch обязателен.

### Типовой тик (на примере событий)

1. Отдельный scope: выбрать **только id** пачки (`Take(BatchSize)`), scope закрыть.
2. Для каждого id — **новый scope и новый DbContext** → handler.
   Почему scope на элемент: ChangeTracker одного контекста накапливает сущности. Если событие №3 упало на середине,
   его несохранённые комиссии остались бы в контексте и **сохранились бы вместе с событием №4** — прямая дорога к двойному начислению.
   Отдельный контекст даёт изоляцию «по построению», а не на честном слове `ChangeTracker.Clear()`.
   Создание scope и DbContext стоит микросекунды, соединение берётся из пула.
   `BackgroundService` — singleton, а DbContext — scoped, поэтому scope всё равно нужен (иначе DI упадёт на старте).
3. В конце (у outbox — ещё и в начале) — обновить gauge `*_pending` одним `COUNT`.

### Статусы события и повторы

| Статус | Значение | Выбирается снова? |
|---|---|---|
| `Received` (0) | принято, ждёт обработки | да, когда `NextAttemptAtUtc <= now` |
| `Processed` (1) | посчитано (или Profit ≤ 0 — посчитано «ничего») | нет |
| `Unresolved` (2) | пользователь не найден в Partners | да, раз в 30 с (`UnresolvedRetryDelay`) |

Ошибка обработки (Partners недоступен, БД моргнула) → `ScheduleRetryAsync`: `Attempts++`, `LastError` (до 1000 символов),
`NextAttemptAtUtc = now + Retry.NextDelay(attempts)` = `min(2^attempts, 300)` секунд: 2, 4, 8, 16 … 300.

**Решение: повторять бесконечно, без статуса `Failed` и лимита попыток.**
Временные ошибки рано или поздно проходят сами. Но **задержку между попытками оставили обязательно**, иначе
«ядовитое» событие (баг на конкретных данных) стояло бы первым в каждой пачке (сортировка по `CreatedAtUtc`),
и 50 таких событий навсегда забили бы пачку — **head-of-line blocking**. С backoff сломанное событие уезжает всё дальше
и не мешает остальным. Застрявшие видно по `Attempts`/`LastError`. В проде вместо этого был бы dead-letter + алерт.

**Защита от повторной обработки**: handler после загрузки проверяет, что событие всё ещё `Received/Unresolved`.
Вторая линия — уникальный индекс `(ProfitEventId, Level)`.

**`ProcessedAtUtc`** ставится только для `Processed`, не для `Unresolved`.

**Метрики после коммита.** `commissions_accrued_*` увеличиваются только после успешного `SaveChangesAsync` —
откатившаяся транзакция не должна попадать в цифры.

### Почему не готовые библиотеки

| Вариант | Почему нет |
|---|---|
| Hangfire / Quartz | тяжело для трёх простых опросов; своя таблица-очередь прозрачнее и сама по себе объяснима |
| MassTransit + брокер | см. раздел 5 |
| `FOR UPDATE SKIP LOCKED` + lease (аренда строки) | обсуждалось: даёт настоящую параллельную обработку несколькими экземплярами; решили, что для тестового достаточно active/standby, а масштабирование обработки — через Kafka/партиции (в README) |

## 8. Схема начисления

- Хранится в `settings` (ключ-значение): `commission_schema = "Linear" | "Fibonacci"`. Ключ — константа `SettingKeys.CommissionSchema`.
- Enum хранится **строкой** (`HasConversion<string>()`) — в базе сразу видно, что выбрано.
- **Схема фиксируется в событии в момент приёма** (`ProfitEvent.SchemaType`), а комиссия копирует её из события.
  Поэтому:
  - переключение влияет только на события, пришедшие после;
  - повторная обработка после сбоя даёт тот же результат (детерминизм);
  - требование «каждая комиссия хранит schema_type» выполнено буквально.
- Альтернатива «читать схему в момент обработки» хуже: событие, пришедшее до переключения, но обработанное после,
  посчиталось бы по новой схеме — неочевидно и недетерминированно.
- **Читается из БД на каждый приём, без кэша.** Кэш в памяти одного экземпляра дал бы разные схемы на разных экземплярах.
  Поиск по PK — практически бесплатен.
- Переключение — `PUT /admin/commission-schema {"schemaType":"Fibonacci"}` → 204. Enum в JSON строкой (`JsonStringEnumConverter`);
  `Enum.IsDefined` проверяет, что не прислали число вроде 5.

### Seed «вставить, если нет», а не `HasData`

`CommissionsDbSeeder` на старте (после миграций):
```sql
INSERT INTO settings ("Key", "Value") VALUES ('commission_schema', 'Linear')
ON CONFLICT ("Key") DO NOTHING
```
**Почему не `HasData`.** `HasData` делает значение частью модели EF: если его когда-нибудь изменить в коде, миграция
сгенерирует `UpdateData` и **молча перезапишет** значение, выставленное админом в рантайме. А если убрать `HasData`,
миграция сгенерирует `DeleteData`. `ON CONFLICT DO NOTHING` никогда не трогает существующее значение и не падает,
если два экземпляра стартуют одновременно.

## 9. Расчёт комиссий

Проект `PartnerCommission.Commissions.Domain` — **без зависимостей** (ни EF, ни HTTP). Поэтому легко тестировать.

- `ICommissionSchema.RateFor(level)` → процент.
  - `LinearSchema`: `return level;`
  - `FibonacciSchema`: предвычисленный `static readonly long[] Sequence` на 93 элемента (`F(0)=0, F(1)=1, F(2)=1, …, F(92)`).
- `CommissionSchemas.For(type)` — switch на два статических экземпляра, неизвестное значение → `ArgumentOutOfRangeException`.
- `CommissionCalculator.Calculate(profit, schemaType, beneficiaries)`:
  - `profit <= 0` или нет получателей → пусто;
  - для каждого: `amount = Math.Round(rate × profit / 100, 4, MidpointRounding.AwayFromZero)`;
  - `amount > 0` → в результат (нулевые после округления не пишем);
  - **уровень берётся из входных данных, а не из позиции в списке** (не полагаемся на порядок ответа Partners);
  - калькулятор **ничего не знает о глубине**: считает по всем предкам, которых получил. Глубину ограничивает Partners.
  - Зарегистрирован **singleton** — без состояния.

### Решения и почему

| Решение | Почему | Альтернатива |
|---|---|---|
| Нумерация `F(1)=1, F(2)=1` | стандартная; прямой партнёр получает 1% | `F(1)=0` → прямой партнёр получает 0% — выглядит как баг |
| Массив `long` на 92 уровня, заполняется один раз | потокобезопасно (только чтение), без переполнения до F(92) ≈ 7.5·10^18 | изначально был `Dictionary<int,int>` с дозаполнением: **небезопасен при параллельных вызовах** (общий экземпляр) и `int` переполнялся на ~47 уровне; тесты это поймали |
| `decimal`, 4 знака | деньги; совпадает с `numeric(18,4)` в БД | `double` — ошибки двоичного представления |
| `AwayFromZero` | привычное «коммерческое» округление: 0.00005 → 0.0001 | `ToEven` (банковское, по умолчанию в .NET) — честнее статистически, но неочевидно проверяющему |
| Нулевые суммы не храним | строка на 0.0000 бессмысленна | хранить — мусор в истории |

Полезные факты для README и разговоров: на 10 уровнях Linear раздаёт **55%** прибыли (1+…+10), Fibonacci — **143%** (1+1+2+…+55).
Уровень > 92 → исключение в Fibonacci; невозможно, т. к. `MaxDepth` ограничен 25.

## 10. Дерево партнёров и рекурсивные CTE

### Хранение: adjacency list

`users (Id uuid PK, ExternalId varchar(64) UNIQUE, ParentId uuid NULL FK→users.Id, CreatedAtUtc)`, индекс на `ParentId` (EF создаёт для FK).
Каждый хранит ссылку на своего партнёра. Назначить/сменить партнёра — один `UPDATE`.

### Альтернативы хранения деревьев

| Способ | Как устроен | Чтение | Запись / перенос ветки | Итог |
|---|---|---|---|---|
| **Adjacency list (выбран)** | `ParentId` в строке | рекурсивный CTE, до N шагов по индексу | 1 UPDATE | оптимален при малой глубине (10) и частых переназначениях |
| Closure table | таблица «предок–потомок–расстояние», все пары | один JOIN, очень быстро | перенос ветки = удалить/вставить много пар | окупается при глубоких деревьях и редких изменениях |
| Materialized path / `ltree` | строка пути `u1.u2.u5` | `LIKE 'u1.u2.%'` / операторы ltree | перенос ветки = переписать путь всем потомкам | удобно для поиска поддеревьев, дорого при переносе |
| Nested sets | числа left/right | поддерево одним диапазоном | вставка сдвигает половину таблицы | для почти статичных деревьев |

### Как работает рекурсивный CTE (`WITH RECURSIVE`)

Файл `Partners.Api/Data/UserTreeQueries.cs`. Пример — предки пользователя:

```sql
WITH RECURSIVE up AS (
    -- (1) нерекурсивная часть (anchor): прямой партнёр
    SELECT p."Id", p."ExternalId", p."ParentId", 1 AS "Level"
    FROM users u
    JOIN users p ON p."Id" = u."ParentId"
    WHERE u."Id" = @userId

    UNION ALL

    -- (2) рекурсивная часть: партнёр того, кого нашли на прошлом шаге
    SELECT p."Id", p."ExternalId", p."ParentId", up."Level" + 1
    FROM up
    JOIN users p ON p."Id" = up."ParentId"
    WHERE up."Level" < @maxDepth          -- (3) ограничитель
)
SELECT "Id", "ExternalId", "ParentId", "Level" FROM up ORDER BY "Level"
```

Как Postgres это выполняет (итеративно, не рекурсивно по стеку):

1. Выполняет anchor → получает строки уровня 1. Кладёт их **и в результат, и в «рабочую таблицу»** (working table).
2. Выполняет рекурсивную часть, где `up` = **только рабочая таблица с прошлого шага** (не весь результат).
   Получает строки следующего уровня → добавляет в результат, они становятся новой рабочей таблицей.
3. Повторяет шаг 2, пока рекурсивная часть не вернёт **пустоту** (дошли до корня: `ParentId IS NULL` → JOIN ничего не даёт)
   **или** не упрёмся в `Level < maxDepth`.
4. Результат — объединение всех шагов.

Пошагово на цепочке `d0 ← d1 ← d2 ← d3`, запрос предков `d3`:

| Шаг | Рабочая таблица (что нашли) | Level | Почему |
|---|---|---|---|
| anchor | d2 | 1 | `ParentId` у d3 → d2 |
| итерация 1 | d1 | 2 | `ParentId` у d2 |
| итерация 2 | d0 | 3 | `ParentId` у d1 |
| итерация 3 | ∅ | — | у d0 `ParentId = NULL`, JOIN пуст → стоп |

**`UNION ALL`, а не `UNION`**: `UNION` удалял бы дубликаты (лишняя работа), в дереве их нет.

**Защита от циклов.** Если бы в данных оказался цикл (`a → b → a`), рекурсия никогда не вернула бы пустоту.
`WHERE Level < maxDepth` гарантирует завершение в любом случае. (В Postgres 14+ есть ещё `CYCLE ... SET is_cycle USING path`,
но с лимитом глубины он не нужен.) Циклы при этом запрещены на уровне правил (ниже).

Три запроса в `UserTreeQueries`:
- `GetAncestorsAsync(userId, maxDepth)` — вверх, как выше.
- `GetDescendantsAsync(userId, maxDepth)` — вниз: anchor `WHERE c."ParentId" = @userId`, рекурсия `JOIN users c ON c."ParentId" = d."Id"`.
  Возвращает **плоский список** строк `(Id, ExternalId, ParentId, Level)`.
- `GetSubtreeHeightAsync(userId, maxDepth)` — тот же обход вниз, но `SELECT COALESCE(MAX("Level"), 0) AS "Value"`
  (EF 8 для скалярного `SqlQuery<int>` ожидает колонку с именем `Value`).

Технические детали EF:
- `Database.SqlQuery<T>($"...")` — интерполированная строка превращается в **параметры**, SQL-инъекции нет.
- Колонки в кавычках: EF создал их в PascalCase (`"ParentId"`), без кавычек Postgres приведёт имя к нижнему регистру и не найдёт.
- `ORDER BY` внутри SQL, без LINQ-композиции поверх — EF не пытается оборачивать CTE в подзапрос.

### Сборка вложенного дерева в C#

```csharp
var childrenByParent = descendants.ToLookup(x => x.ParentId);
IReadOnlyList<TreeNodeDto> BuildChildren(Guid parentId) => childrenByParent[parentId]
    .Select(x => new TreeNodeDto(x.ExternalId, x.Level, BuildChildren(x.Id)))
    .ToList();
```
Один запрос в БД, затем группировка по `ParentId` в памяти и рекурсивная сборка. Было до переработки — по запросу на каждый узел (N+1).

`GET /users/{id}/tree` возвращает **всё** дерево (решение пользователя: без параметра `down`). По глубине ограничено `MaxDepth`,
по ширине — нет (ограничение, записано в README).

### Правило глубины — инвариант дерева

Задание: «глубину дерева ограничить (например, 10)». Два прочтения:
- (а) ограничивать только при чтении — дерево может быть любым, отдаём не больше N предков;
- **(б) ограничить само дерево — выбран**: ни у одного пользователя не может быть больше `MaxDepth` (10) предков.

Плюс (б): дерево всегда валидно, комиссии никогда не «обрезаются» молча, все запросы ограничены по построению.

Проверка при назначении партнёра:
- `A` — число предков у партнёра;
- `h` — высота ветки пользователя (насколько глубоко уходят его потомки, 0 — нет потомков);
- после привязки у самого глубокого потомка будет `h + 1 + A` предков; требование **`h + 1 + A ≤ MaxDepth`**.

Пример: MaxDepth 10, у партнёра 7 предков, у пользователя внуки (h = 2): 2 + 1 + 7 = 10 — можно; правнуки — 11 — нельзя.

**Глубиной владеет Partners.** Commissions просто берёт «всех предков», калькулятор глубину не знает.
Минус (осознанный): число оплачиваемых уровней зависит от конфига другого сервиса; зато настройка одна.

### `SetPartnerAsync` по шагам

1. `externalId == partnerExternalId` → **400** (сам себе, дешёвая проверка до БД).
2. `strategy = CreateExecutionStrategy()`; всё внутри `strategy.ExecuteAsync(...)`:
   с `EnableRetryOnFailure` открывать транзакцию вручную можно только так — стратегия умеет повторить транзакцию целиком.
   Первым делом `ChangeTracker.Clear()` — при повторе начинаем с чистого контекста.
3. `BeginTransaction` → `SELECT pg_advisory_xact_lock(42)` — **все изменения дерева по одному**.
4. Загрузить пользователя и партнёра → нет → **404**.
5. Уже этот партнёр → «unchanged», **204**, ничего не меняем (идемпотентно).
6. Предки партнёра (`maxDepth + 1` — **с запасом**: если вернулось больше `maxDepth`, цепочка уже слишком длинная) и высота ветки пользователя.
7. `PartnerLinkRules.Check(...)` — **чистая функция**, покрыта тестами:
   - `userId == partnerId` → SelfReference (400);
   - пользователь среди предков партнёра → **Cycle** (409): значит партнёр — его потомок;
   - `h + 1 + A > maxDepth` → **DepthExceeded** (409).
8. `ParentId = partner.Id`, `SaveChanges`, `Commit`.

**Почему нужна блокировка.** Без неё два параллельных запроса `u1 → u2` и `u2 → u1` оба проверят «цикла нет»
(каждый видит базу без изменения другого) и оба сохранятся → цикл. `pg_advisory_xact_lock` — транзакционная блокировка,
снимается сама при commit/rollback. Второй запрос ждёт и проверяет уже обновлённые данные.
Изменения дерева редкие, поэтому одна глобальная блокировка не мешает.
Альтернатива — изоляция `Serializable` с повтором на `40001`: тоже работает, но сложнее объяснить и отладить.

`DeletePartnerAsync` без проверок и блокировки: удаление связи не создаёт цикл и не увеличивает глубину.

## 11. Advisory-блокировки PostgreSQL

**Что это.** Блокировки «по договорённости»: Postgres не связывает их с таблицами, это просто число-ключ, которое
приложения согласились использовать. Действуют **в пределах одной базы** (разные сервисы с разными БД не мешают друг другу даже с одинаковым ключом).

| Вид | Функция | Держится | Где у нас |
|---|---|---|---|
| Транзакционная | `pg_advisory_xact_lock(key)` | до конца транзакции | изменение дерева (ключ 42) |
| Сессионная, ждущая | `pg_advisory_lock(key)` | пока не `unlock` или не закроется соединение | не используем: ждёт вечно и не реагирует на CancellationToken |
| Сессионная, пробующая | `pg_try_advisory_lock(key)` → true/false | то же | `AdvisoryLock` (Shared/Data): миграции и фоновые задачи |

### Ключи

| Ключ | База | Зачем |
|---|---|---|
| 42 | partners | изменения дерева (xact) |
| 52 | каждая | миграции на старте |
| 53 | wallets | `PayoutProcessor` |
| 54 | commissions | `OutboxDispatcher` |
| 55 | commissions | `ProfitEventProcessor` |

### Класс `AdvisoryLock`

- `TryAcquireAsync(db, key)`: **сам открывает соединение DbContext** (`OpenConnectionAsync`) — EF его потом не закроет,
  и все запросы этого контекста идут по той же сессии, что держит блокировку. `pg_try_advisory_lock` → если `false`,
  закрывает соединение и возвращает `null`.
- `DisposeAsync`: `pg_advisory_unlock` + `CloseConnectionAsync`. **Снимать явно обязательно**: соединение возвращается в пул Npgsql
  и без unlock блокировка висела бы на нём (Npgsql сбрасывает состояние сессии лениво — при следующем использовании соединения).
- Упал процесс → соединение рвётся → Postgres снимает блокировку сам. Вечных блокировок не бывает.
- Выполнение через ADO (`DbCommand`), а не `SqlQuery<bool>` — проще и надёжнее с параметрами.

### Active/standby для фоновых задач

Каждый тик: взял блокировку → работаю; не взял → пропускаю тик (Debug-лог). Лидер упал → блокировка освобождена → следующий тик берёт другой экземпляр.
Итог: **API масштабируется свободно, фоновая работа идёт на одном экземпляре одновременно.**

**Главная причина — гонка выплат** (раздел 12). Для outbox — убирает двойную доставку (хотя Wallets её и так переживёт).
Для событий — убирает лишнюю повторную обработку (хотя уникальный индекс не дал бы задвоить).

**Известная теоретическая дыра**: если соединение с блокировкой оборвётся посреди длинного тика, Postgres снимет блокировку,
а работа продолжится → второй экземпляр может начать ту же работу. Страховка (не сделана, решено «слишком для тестового»):
атомарный `UPDATE wallets SET "Balance" = "Balance" + @sum` или concurrency token `xmin` на `Wallet`.

### Почему не `FOR UPDATE SKIP LOCKED`

`SELECT ... FOR UPDATE SKIP LOCKED LIMIT N` даёт каждому экземпляру **свою** пачку строк — настоящую параллельную обработку.
Но: держать транзакцию открытой во время HTTP-вызова к Partners плохо (долгие транзакции, соединения), а с `EnableRetryOnFailure`
ручная транзакция требует execution strategy. Правильный вариант — «захват с арендой» (UPDATE ... SET Status=Processing, LockedUntil=now+5m
... WHERE Id IN (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING Id) — был спроектирован, но решено упростить до active/standby.
Масштабирование обработки в проде — Kafka с партициями по `UserExternalId`.

## 12. Кошельки и выплаты

### Модель

- `wallet_entries`: `CommissionId` (PK, `ValueGeneratedNever` — приходит извне), `UserExternalId`, `EventExternalId`, `Amount numeric(18,4)`,
  `Status` (`Pending`/`Paid`, строкой), `AccruedAtUtc`, `ReceivedAtUtc`, `PaidAtUtc`.
  Индексы: `(UserExternalId, Status)`, `(UserExternalId, PaidAtUtc)`, `(Status)`.
- `wallets`: `UserExternalId` (PK), `Balance numeric(18,4)`, `UpdatedAtUtc`.
- Связи (FK) между ними нет: записи приходят раньше, чем создаётся кошелёк (кошелёк создаётся при первой выплате).

### Два этапа

- **Начисление**: Wallets узнал о комиссии (`Pending`). На баланс не влияет.
- **Выплата**: периодическая задача переводит накопленное в `Paid` и увеличивает баланс.
  Это ровно формулировка задания: «баланс = сумма выплаченных», «периодическая выплата накопленных».

### `PayoutHandler` — одна транзакция на пользователя

```
entries = все Pending этого пользователя (tracked)
wallet  = найти или создать (Balance 0)
entries → Paid, PaidAtUtc = now
wallet.Balance += сумма
SaveChanges  — одна транзакция: либо всё, либо ничего
метрики payouts_total / payout_amount_total — после коммита
```
Ошибка → Warning, записи остались `Pending`, попадут в следующую выплату (без отдельного механизма повторов — здесь нет внешних вызовов).

`EnableRetryOnFailure` может повторить `SaveChanges`, если коммит прошёл, а ответ потерялся. Это безопасно:
EF пишет **абсолютное значение** баланса (`SET "Balance" = 5.0000`), а не прибавку, так что повтор не удвоит.

### Гонка выплат — почему нужна блокировка (разбор)

Два экземпляра, без блокировки, уровень изоляции Read Committed (каждый запрос видит последние закоммиченные данные):
1. B читает `Pending` записи пользователя → видит E1 на 100 (A ещё не закоммитил).
2. A коммитит: E1 → Paid, баланс 0 → 100.
3. B читает кошелёк → уже видит баланс 100 (коммит A).
4. B считает `100 + 100 = 200`, помечает E1 Paid, коммитит → **E1 выплачена дважды в балансе**.

Между двумя чтениями B «мир» успел измениться — так и работает Read Committed. Лечится тем, что выплату делает один экземпляр (advisory lock 53).

### Баланс хранимый, а не вычисляемый

Альтернатива — `SUM(Amount) WHERE Paid` на каждый запрос баланса. Плюс — не может разойтись. Минус — нет сущности «кошелёк»
(а в задании она есть), и чтение дороже. Выбран хранимый: меняется только в транзакции выплаты вместе со статусами,
расходиться не с чем. Проверка инварианта одним запросом: `Balance = SUM(Amount WHERE Paid)`.

### Эндпоинты Wallets

- `GET /users/{id}/wallet` → `{"balance": ...}`; кошелька нет → **200 с нулём** (Wallets не знает, существует ли пользователь — это знает Partners;
  «пустой кошелёк» — корректный ответ). GET **ничего не создаёт** (раньше создавал — убрали: GET не должен менять данные и гонялся с выплатой).
- `GET /users/{id}/wallet/payouts` — только `Paid`, свежие первыми (`PaidAtUtc desc, CommissionId desc`), пагинация.
- `POST /internal/commissions` — приём из outbox, идемпотентен по `CommissionId`, 204 и на новое, и на повтор; сумма ≤ 0 → 400; те же id с другими данными → 409.
- `POST /internal/commissions/payments:query` — статусы по списку id (`PaidAtUtc` или null). Нет в ответе = Wallets ещё не получил.

## 13. Надёжность

### Resilience на HttpClient

`AddStandardResilienceHandler()` (пакет `Microsoft.Extensions.Http.Resilience`) — готовый конвейер Polly:
- **retry** с экспоненциальной задержкой на 5xx, 408, 429, сетевые ошибки, таймауты (404 не повторяет — нам и нужно);
- **circuit breaker**: если сосед часто падает, запросы на время сразу отбиваются, не нагружая его;
- таймаут на попытку и общий (~30 с).

Повторяет и POST — безопасно, потому что все наши приёмники идемпотентны.

Порядок обработчиков: метрики HttpClient зарегистрированы **после** resilience → оказываются **внутри** него → каждая попытка
замеряется отдельно (видно «503, потом 200»). Цепочкой `.AddStandardResilienceHandler().UseHttpClientMetrics()` не пишется —
первый метод возвращает другой тип, поэтому вызовы разнесены в `Program.cs` Commissions.

Минус: при лежащем Wallets детали события отвечают `Unknown` только через ~30 с (общий таймаут). Можно было дать этому клиенту
короткий таймаут — не сделано.

### Graceful shutdown

- `docker stop` → SIGTERM → хост начинает остановку: перестаёт принимать запросы, отменяет `stoppingToken` фоновых задач,
  ждёт до `HostOptions.ShutdownTimeout` (**10 с**, `ServiceDefaultsExtensions.ShutdownTimeout`).
- **Ловушка**: Docker по умолчанию через 10 с шлёт SIGKILL. Поэтому в compose `stop_grace_period: 35s` (больше таймаута хоста).
- Прерванная работа безопасна: всё значимое делается в транзакциях → незакоммиченное просто повторится.
- Проверено: `docker compose stop <svc>` → exit code 0, в логе `Application is shutting down...`.

### Health checks

- `/health/live` — «процесс жив», без проверок зависимостей (`Predicate = _ => false`).
- `/health/ready` — «готов обслуживать»: проверки с тегом `ready` = только **собственная** БД (`AddNpgSql`).
  Соседей в readiness не включаем: иначе падение Partners сделало бы «неготовыми» все сервисы каскадом.
- Статус проверок ещё и метрикой `aspnetcore_healthcheck_status` (`ForwardToPrometheus`).
- В compose healthcheck контейнера — `curl -fsS http://localhost:8080/health/ready` (curl доустановлен в образ, в `aspnet` его нет).

## 14. Миграции на старте

`app.Services.MigrateWithLockAsync<TContext>()` (Shared/Data/MigrationExtensions) сразу после `builder.Build()`:
1. Таймаут 2 минуты (не висеть вечно).
2. В цикле `AdvisoryLock.TryAcquireAsync(key 52)`; занято → «waiting…», пауза 1 с.
3. Под блокировкой: `GetPendingMigrationsAsync` → пусто → «is up to date»; иначе `MigrateAsync` (на той же сессии).
4. Блокировка снимается в `await using`.

**Почему блокировка.** В EF Core 8 нет своей блокировки миграций (появилась в EF 9). Два экземпляра одного сервиса,
стартовав вместе, начали бы применять одну миграцию, и один упал бы. Проверено на двух копиях: одна применила, вторая ждала и увидела «up to date».

- Порядок в Commissions: **миграции → seed схемы → запуск** (seed нужна таблица `settings`).
- **База должна уже существовать**: блокировка берётся на соединении к ней. В compose базы создаёт `infra/postgres-init/01-create-databases.sql`
  (выполняется только при первом создании тома!), локально — вручную или `dotnet ef database update`.
- **Одна миграция `Initial` на сервис** — до релиза нормально: история фикс-миграций проверяющему ничего не даёт.
  Пересоздание разрешено, пока данные одноразовые и схему никто больше не применял.
- Раз миграции применяются автоматически, каждую новую **нужно просматривать** перед коммитом (молча применится и `DropColumn`, и `DeleteData`).
- Альтернативы в проде: отдельный контейнер-мигратор (`depends_on: service_completed_successfully`) или EF migration bundle.

## 15. API: принятые решения

| Решение | Почему | Альтернатива |
|---|---|---|
| Приём события → **202 Accepted** + `Location` | обработка асинхронная, «принято, считаем» | 200/201 — вводит в заблуждение |
| Повтор события → **200** с текущим статусом | клиент видит, что уже обработано | 409 — клиенту пришлось бы обрабатывать «ошибку» на нормальный повтор |
| Создание пользователя → **201** + `Location`, повтор → **200** | идемпотентное создание | 409 на дубль |
| Партнёр — **`PUT /users/{id}/partner`** | связь — ресурс пользователя; PUT идемпотентен по стандарту | `POST /users/{id}:set-partner` (custom method) — допустимо, но не классический REST |
| Префикс **`/internal/...`** для межсервисных | видно, что это контракт между сервисами, закрывается на gateway | общие эндпоинты для людей и сервисов |
| `POST .../payments:query` | чтение с телом: GUID'ы переполняют URL; двоеточие = custom method («действие») | `GET ?ids=` — длинный URL; HTTP `QUERY` — черновик стандарта |
| Пути `/users/{id}/wallet`, `/users/{id}/profit-events` | клиенту API выглядит единым вокруг пользователя | `/wallets/{id}` — проще роутинг на gateway, но видна внутренняя кухня |
| `ExternalId` в путях, не Guid | снаружи система знает пользователей по внешним id | внутренние Guid |
| **Offset-пагинация** `?page=&pageSize=` (1..100, по умолчанию 20) | проще, понятна любому ревьюеру | keyset (`WHERE (CreatedAt, Id) < (...)`) — нет дублей при вставках, быстро на любой глубине; указано как развитие |
| Однозначная сортировка (`ThenBy(Id)`) | при равном времени записи не «прыгают» между страницами | — |
| `PageRequest` — класс с `init` и параметр **`paging`**, не `page` | ловушка model binding: параметр `page` + ключ `?page=` → биндер считает `page` префиксом и ищет `page.Page`, значения молча не привязываются | — |
| Страница за пределами данных → 200, пустой `items` | это не ошибка | 404 |

Ответ списков: `{ items, page, pageSize, totalCount }` (`PagedResponse<T>`, расширение `ToPagedAsync` в Shared).

## 16. Ошибки

- Свои исключения в `Shared/Exceptions`: `NotFoundException` (404), `ConflictException` (409); `ValidationException` из DataAnnotations (400).
- Один глобальный `ApiExceptionHandler : IExceptionHandler` (.NET 8) превращает их в **ProblemDetails** (RFC 7807)
  через `IProblemDetailsService`. В каждый ответ добавляется `traceId` (`CustomizeProblemDetails`) — по нему ошибка находится в логах всех сервисов.
- Неизвестное исключение → логируется Error сам обработчиком, возвращает `false` → стандартный 500 ProblemDetails.
- Клиент оборвал запрос (`OperationCanceledException` + `RequestAborted`) → Debug-лог, код 499, **не** Error.
- Фильтр логов `ExceptionHandlerMiddleware → None`: в .NET 8 middleware пишет `fail` даже по обработанным исключениям (шум).
- Валидация входа — атрибуты на record'ах + `[ApiController]` → 400 автоматически, до вызова метода.
  `decimal? Profit` + `[Required]`: у не-nullable `decimal` отсутствующее поле молча стало бы 0 (баг, пойман в ревью).

**Почему исключения, а не Result-паттерн.** `Result<T>`/`OneOf` честнее по типам и без стоимости исключений, но на трёх небольших
сервисах добавляют много шаблона в каждый контроллер. Исключения + один обработчик — стандарт ASP.NET Core, ревьюер узнаёт сразу.

## 17. Наблюдаемость

### Логи

Всё в `ServiceDefaultsExtensions.AddLogging`:
- `ActivityTrackingOptions = TraceId | SpanId | ParentId` — ID текущего `Activity` попадает в scope каждой записи.
- Формат выбирается конфигом `Logging:Console:FormatterName`: `simple` (одна строка, со scope) или `json` (с полями, UTC).
- **Ловушка, пойманная при проверке**: если `FormatterName` не задан, `ConsoleLoggerProvider` идёт по устаревшей ветке совместимости
  и **перезаписывает** настройки simple-форматтера полями `ConsoleLoggerOptions` (`IncludeScopes = false`). Лечение —
  `o.FormatterName ??= "simple"`.
- **Ловушка №2**: `BeginScope(new Dictionary<string, object>{...})` в simple-формате печатается как `System.Collections.Generic.Dictionary`2[...]`
  (форматтер вызывает `ToString()`). Правильно — шаблон: `BeginScope("EventExternalId: {EventExternalId}", id)` — читается в тексте и структурирован в JSON.
- Используется встроенный логгер, **без Serilog** — всё нужное (scope, TraceId, JSON) есть из коробки.

### Трассировка (сквозной TraceId)

- Для HTTP: ASP.NET сам создаёт `Activity` на запрос, HttpClient сам передаёт заголовок W3C `traceparent` → у вызова Commissions → Wallets тот же TraceId.
- Для фоновых задач запроса нет → нет TraceId. Решение (`Shared/Diagnostics/Tracing.cs`):
  - свой `ActivitySource("PartnerCommission")`;
  - **`ActivityListener` на этот источник** — без подписчика `StartActivity` возвращает `null` (OpenTelemetry у нас нет, значит слушателя тоже нет);
    регистрируется один раз из `AddServiceDefaults`;
  - handler'ы первой строкой: `using var activity = Tracing.Source.StartActivity("ProcessProfitEvent" | "DispatchOutboxMessage" | "PayoutUser")`
    + теги с id → у обработки события свой TraceId, и он уходит в запрос к Partners.
- Проверено: логи Commissions и Partners по одному событию — один TraceId; то же для outbox → Wallets.
- Ограничение: обработка события и доставка в Wallets — **разные трассы** (связаны через `EventExternalId`). Объединить — хранить `traceparent`
  в строке outbox (новая колонка, не делали). Экспорта трасс в Jaeger/Tempo нет.

### Метрики (prometheus-net)

Почему prometheus-net, а не OpenTelemetry: экспортёр OTel в Prometheus был prerelease; prometheus-net стабилен и проще.

Автоматические (из `ServiceDefaults`):
- `UseHttpMetrics()` — входящие HTTP; стоит **снаружи** обработчика ошибок, чтобы писался итоговый код (404/409), а не «исключение»;
- `UseHttpClientMetrics()` — исходящие из Commissions;
- `ForwardToPrometheus()` — health checks;
- `process_*`, `dotnet_*` — по умолчанию;
- `MapMetrics()` → `/metrics`.

Бизнес-метрики — статические классы `Observability/*Metrics.cs` в каждом сервисе, префикс `partnercommission_`:

| Сервис | Метрика | Тип | Метки |
|---|---|---|---|
| Partners | `users_created_total` | counter | result: created, duplicate |
| Partners | `partner_links_total` | counter | result: linked, unchanged, self, cycle, depth_exceeded |
| Commissions | `profit_events_received_total` | counter | result: accepted, duplicate |
| Commissions | `profit_events_processed_total` | counter | outcome: processed, unresolved, retry |
| Commissions | `profit_event_processing_seconds` | histogram | — |
| Commissions | `commissions_accrued_total` / `_amount_total` | counter | schema |
| Commissions | `outbox_messages_sent_total` | counter | result: sent, failed |
| Commissions | `outbox_pending`, `profit_events_pending` | gauge | — |
| Wallets | `commissions_received_total` | counter | result: created, duplicate, conflict |
| Wallets | `payouts_total`, `payout_amount_total` | counter | — |
| Wallets | `payout_run_seconds` | histogram | — |
| Wallets | `wallet_entries_pending` | gauge | — |

Правила:
- **В метках никогда нет id** (пользователя, события): каждая уникальная метка = отдельный временной ряд, Prometheus захлебнётся.
- Счётчики только растут; «в секунду» считает Prometheus: `rate(x_total[1m])`.
- Деньги в метриках — `double`, это для графиков; источник правды — БД.
- Счётчики денег/начислений — **после коммита**.
- Успех `partner_links` считается **после** `strategy.ExecuteAsync` (стратегия может повторить лямбду → посчиталось бы дважды).
- Gauge `*_pending` пишет только лидер → в PromQL агрегировать через **`max()`**, не `sum()`.
- `outbox_pending` обновляется **и в начале, и в конце** тика: при лежащем Wallets один тик длится долго (≈30 с таймаута на сообщение),
  и обновление только в конце показывало бы 0 именно в момент аварии (нашлось на финальном прогоне).

Prometheus в compose (`infra/prometheus/prometheus.yml`, опрос 5 с, UI `:9090`). Grafana — решено не добавлять.

## 18. Конфигурация

- Options-паттерн + `ValidateDataAnnotations().ValidateOnStart()` — неверное значение роняет сервис **при старте** с понятным сообщением,
  а не на первом использовании.
- `PartnersOptions.MaxDepth` (секция `Partners`, по умолчанию 10, допустимо 1..25).
- **Фоновые задачи**: `PollingJobOptions { PollInterval (1 с..1 ч), BatchSize (1..1000) }` — **named options** по имени класса задачи:
  секция `BackgroundJobs:{ProfitEventProcessor|OutboxDispatcher|PayoutProcessor}`.
  Регистрация одной строкой `services.AddPollingJob<TJob>()` (привязка секции + валидация + `AddHostedService`).
  Чтение в базовом классе `IOptionsMonitor<PollingJobOptions>.Get(JobName)` — только у `IOptionsMonitor` есть `Get(name)`;
  `IOptionsSnapshot` не подходит — он scoped, а `BackgroundService` singleton.
- Значения: события 5 с, outbox 5 с, выплаты 15 с, пачка 50 (в `appsettings.json` сервисов).
- Любой ключ переопределяется переменной окружения, `:` → `__` (`BackgroundJobs__PayoutProcessor__PollInterval=00:00:03`).
- Строки подключения — в `appsettings.Development.json` (локально) и в environment compose (`Host=postgres`: внутри контейнера `localhost` — это сам контейнер).

## 19. Shared и Contracts

- **`PartnerCommission.Shared`** — инфраструктура, одинаковая для всех сервисов:
  `Hosting` (ServiceDefaults, PollingBackgroundService, PollingJobOptions, Retry), `Data` (AdvisoryLock, MigrationExtensions,
  DbUpdateExceptionExtensions), `Exceptions`, `Pagination`, `Diagnostics` (Tracing).
- **`PartnerCommission.Contracts`** — DTO между сервисами, **без зависимостей**: `AncestorsResponse/AncestorItem`, `CommissionAccruedMessage`,
  `CommissionPaymentsQuery`, `CommissionPaymentResponse`.
- **Почему раздельно**: у них разные причины меняться. Инфраструктуру меняют свободно; контракт — это API между сервисами, менять только
  совместимо (добавлять поля). В одной сборке граница размылась бы и сервис, которому нужен один DTO, тянул бы всю инфраструктуру.
- **Что туда нельзя**: доменные сущности, DbContext, бизнес-логику — иначе сервисы связаны через общий код и выкатываются вместе.
- В проде Contracts был бы NuGet-пакетом с версионированием. Каноничная альтернатива — дублировать DTO в каждом сервисе.
- `ServiceDefaults` по мотивам .NET Aspire: `builder.AddServiceDefaults()`, `app.UseServiceDefaults()`, `app.MapDefaultEndpoints()` — в каждом `Program.cs` по строке.

## 20. Docker и docker-compose

**Dockerfile** (по одному в каждом сервисе; решено три отдельных, а не один с параметром):
- Контекст сборки — **корень репо** (сервисам нужны Shared/Contracts/Domain).
- Сначала копируются только `.csproj` → `dotnet restore` → потом код → `publish`. Слой пакетов кэшируется и не качается заново при правке кода.
- Runtime `aspnet:8.0` + `curl` (для healthcheck), `USER app` (встроенный непривилегированный пользователь .NET 8), порт 8080.

## 22. Известные ограничения

Осознанно оставлены (часть откачена как «слишком для тестового»):

| Ограничение | Почему так / как лечится |
|---|---|
| Повтор события с Profit, где > 4 знаков, → 409 вместо 200 | база округляет до `numeric(18,4)`; лечится `Math.Round` при приёме |
| Profit > 14 цифр до запятой → 500 | переполнение `numeric(18,4)`; лечится `[Range(typeof(decimal), ...)]` с invariant culture |
| Фоновая обработка на одном экземпляре | active/standby; масштаб — Kafka по `UserExternalId` или SKIP LOCKED + lease |
| Потеря advisory lock посреди тика | теоретическая гонка выплат; атомарный UPDATE баланса или `xmin` |
| Событие и доставка — разные трассы | `traceparent` в outbox |
| `/internal/*` без аутентификации | gateway / mTLS / API keys |
| Offset-пагинация | keyset для лент |
| Миграции на старте | отдельный мигратор / bundle |
| «Ядовитые» элементы повторяются вечно | dead-letter + алерт |
| Широкое дерево возвращается целиком | лимит узлов / пагинация детей |
| Детали события при лежащем Wallets ждут ~30 с | отдельный клиент с коротким таймаутом |
| Только unit-тесты | Testcontainers |

## 24. Вопросы, которые могут задать

**Как гарантируется отсутствие двойных начислений?**
Уникальные ключи в БД на каждом шаге (событие, уровень комиссии, id комиссии в Wallets) + паттерн проверка/вставка/catch,
транзакция «комиссии + outbox + статус», идемпотентный получатель outbox, блокировка на выплату.

**Почему не Kafka?**
Задание разрешает HTTP + Outbox. Outbox всё равно нужен для атомарности «записал в БД и опубликовал». Kafka добавила бы
инфраструктуру, но для масштабирования обработки в проде была бы следующим шагом (партиции по UserExternalId).

**Что будет, если Wallets упадёт?**
Комиссии уже записаны в Commissions, сообщения копятся в outbox (`outbox_pending` растёт), детали события показывают `Unknown`.
Поднимется — диспетчер доставит всё, дубли отсечёт PK.

**Что будет, если упадёт Commissions посреди обработки?**
Транзакция не закоммичена → событие `Received` → после рестарта обработается снова. Ничего не потеряно и не задвоено.

**Как масштабируется?**
API — сколько угодно экземпляров. Фоновые задачи — один активный на advisory lock, остальные на подхвате. Миграции — под блокировкой.

**Почему схема фиксируется при приёме, а не при расчёте?**
Детерминизм повторной обработки и буквальное выполнение «переключение влияет только на новые».

**Как предотвращаются циклы в дереве и почему нужна блокировка?**
Проверка «пользователь среди предков партнёра» + транзакционная advisory-блокировка, иначе два параллельных встречных запроса создадут цикл вместе.

**Как работает рекурсивный CTE?**
Anchor даёт первый уровень, рекурсивная часть на каждом шаге берёт только строки прошлого шага и находит следующий уровень, пока
не вернёт пустоту или не упрётся в лимит уровня; результат — объединение всех шагов.

**Почему adjacency list, а не closure table / ltree?**
Глубина ≤ 10, переназначения — один UPDATE. Остальные ускоряют чтение ценой дорогого переноса ветки.

**Почему баланс хранится, а не считается?**
Кошелёк — сущность из задания; меняется только в транзакции выплаты вместе со статусами, расходиться не с чем.

**Почему бесконечные повторы, а не лимит попыток?**
Временные сбои проходят; экспоненциальная задержка не даёт ядовитым элементам блокировать очередь. В проде — DLQ и алерт.

**Почему исключения, а не Result?**
Стандартный подход ASP.NET Core, один обработчик → ProblemDetails, меньше шаблона на маленьких сервисах.

**Как искать проблему по логам?**
Взять `traceId` из ответа с ошибкой или из лога → он одинаковый во всех сервисах для одного запроса/события; для фоновых — ещё и
scope `EventExternalId` / `OutboxMessageId` / `UserExternalId`.
