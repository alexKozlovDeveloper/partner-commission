# Партнёрские комиссии — памятка по архитектуре (как всё работает и почему)

Цель файла: открыть через год и полностью восстановить в голове систему
partner-commission — каждое решение, его причину, отвергнутые альтернативы и
механику подходов. Написано по финальному состоянию кода на момент сдачи.

---

## 1. Карта системы

```
клиент ──► Partners     (дерево: users, связи, обходы)        БД partners
клиент ──► Commissions  (события, расчёт, схема, outbox)      БД commissions
клиент ──► Wallets      (кошельки, выплаты)                   БД wallets

Commissions ──HTTP──► Partners   GET /internal/users/{id}/ancestors   (цепочка на момент расчёта)
Commissions ──HTTP──► Wallets    POST /internal/commissions           (доставка начислений из outbox)
Commissions ──HTTP──► Wallets    POST /internal/commissions/payments:query  (статус выплат для детализации)
```

Плюс Prometheus в compose, который опрашивает /metrics всех трёх.

**Три зоны владения** (главный аргумент границ): *сеть* — инварианты «нет
циклов, цепочка ≤ 10»; *расчёт* — «событие рассчитано ровно один раз, по
схеме на момент приёма»; *деньги* — «баланс = сумма выплаченного, одна
комиссия — одна выплата». У каждой зоны своя БД, чужие таблицы недоступны
физически (Postgres не умеет JOIN между базами).

- Меньше сервисов → исчезает асинхронный шов, который задание просит показать.
- Больше → деление декоративное: у payout-джоба или админки нет своих данных
  и инвариантов.

**Проекты**: 3 × Api; `Commissions.Domain` (чистый расчёт, ноль зависимостей);
`Contracts` (межсервисные DTO/сообщения); `Shared` (cross-cutting: исключения
+ хендлер, пагинация, AdvisoryLock, PollingBackgroundService, миграции,
ServiceDefaults). Сущности НЕ вынесены в Domain-сборки осознанно: это модели
хранения (форма диктуется EF и статусными машинами), их место рядом с
DbContext; перенос в «Domain» был бы ложным обещанием rich-модели.
Application-слой появится при первом втором потребителе (вынос воркеров).

## 2. Жизнь одного события (сквозной сценарий — держать в голове целиком)

1. `POST /users/{userId}/profit-events {eventExternalId, profit}` →
   Commissions **идемпотентно** сохраняет ProfitEvent со **штампом текущей
   схемы** и статусом Received, отвечает 202 (дубль → 200). Расчёта нет.
2. `ProfitEventProcessor` (поллинг ~5с, один активный экземпляр через
   advisory try-lock) берёт пачку Received/готовых-к-повтору, на каждое
   событие — свой scope и `ProfitEventHandler`.
3. Handler: profit ≤ 0 → сразу Processed. Иначе — HTTP к Partners за
   цепочкой предков (retry + circuit breaker на клиенте). Пользователь
   неизвестен → **Unresolved** + NextAttemptAtUtc (повтор позже, не похороны).
4. Расчёт `CommissionCalculator`'ом по схеме **из штампа события** →
   комиссии + outbox-строки (CommissionAccrued) + статус Processed —
   **одним SaveChanges = одной транзакцией**.
5. `OutboxDispatcher` перекладывает outbox → HTTP POST в Wallets
   `/internal/commissions`. Ошибка → персистентный retry (Attempts,
   экспоненциальный backoff с потолком, LastError).
6. Wallets идемпотентно (PK = CommissionId) заводит `WalletEntry` со
   статусом Pending; дубль с теми же данными — молчаливый OK, с другими —
   409.
7. `PayoutProcessor` (поллинг ~15с, try-lock) по каждому пользователю одной
   транзакцией: entries Pending → Paid + `wallet.Balance += total`.
8. Детализация события в Commissions спрашивает статусы выплат у Wallets
   **синхронно** (`payments:query`); Wallets недоступен → paymentStatus =
   Unknown (деградация вместо падения).

## 3. Решения по одному: как работает / почему / альтернативы

### 3.1 Вход через REST + таблица событий как очередь

**Как работает.** POST только пишет строку и отвечает 202 Accepted («принято,
обработаю»); таблица profit_events со статусами — это входная очередь на
Postgres: буфер сглаживает пики, сбой обработки = «позже», а не «потеряли».

**Почему.** Задание явно разрешает HTTP вместо Kafka; статусная модель даёт
те же гарантии очереди (буферизация, ретраи, невозможность потери) без
брокера.

**Альтернативы.** Kafka-consumer на входе (прод-вариант: точка замены —
только сам POST-эндпоинт, вся механика за ним не меняется); синхронный расчёт
в запросе (отвергнуто: latency, потеря при сбое, ложный 201).

**Почему 202, а не 201:** комиссий в момент ответа ещё НЕТ; 201 «ресурс
создан и вот он» врал бы. 202 — единственный честный код для «взял в работу».

### 3.2 Штамп схемы при приёме (не при расчёте)

**Как.** Колонка profit_events.SchemaType заполняется в момент POST значением
из settings; обработчик settings не читает вообще.

**Почему.** Иначе результат расчёта зависел бы от задержки обработки:
событие пришло при Linear, Partners полежал 10 минут, админ переключил на
Fibonacci — и деньги посчитались не по той схеме. Момент фиксации должен быть
детерминирован. (Это находка ревью первого референса.)

**Альтернатива** — читать при расчёте: проще на одну строку, но
недетерминированно. Требование «переключение влияет только на новые» при
штампе выполняется буквально: новые = принятые после.

### 3.3 Transactional Outbox + доставка HTTP

**Проблема, которую решает.** «Записать комиссии в свою БД» и «сообщить
Wallets» — две системы; общей транзакции нет. Упали между ними → комиссия
есть, Wallets не знает (или наоборот).

**Как работает.** Outbox-строка (Type + Payload JSON + CreatedAt +
ProcessedAt + Attempts/NextAttemptAtUtc/LastError) пишется В ТУ ЖЕ транзакцию
БД, что и комиссии — атомарно по построению. Отдельный OutboxDispatcher
поллит необработанные и доставляет HTTP-вызовом; успех → пометка
ProcessedAtUtc. Упали между доставкой и пометкой → повторная доставка.

**Следствие — гарантия at-least-once**: дубли доставок штатны, поэтому
получатель ОБЯЗАН быть идемпотентным (см. 3.7). Exactly-once дёшево не
существует: доставка и подтверждение — две операции, между ними всегда можно
упасть.

**Почему одна таблица, а не по типу сообщения**: outbox — транспортный
конверт; Type говорит, во что десериализовать. Новый тип сообщения = новый
case у диспетчера, ноль миграций. Таблица-на-тип = миграция и новый поллер на
каждый тип (отвергнуто).

**Альтернативы**: брокер (RabbitMQ/Kafka) — план развития, outbox остаётся,
меняется только «нога доставки» (Publish вместо HTTP POST); встроенный
EF-outbox MassTransit — скрыл бы механику, самописный выбран ради
прозрачности для ревью.

### 3.4 Идемпотентность приёма: check + insert + catch(23505)

**Как работает** (одинаково для POST users и POST events):
1) проверка существующего по ExternalId → «дубль» как нормальный результат
   (оптимизация счастливого пути);
2) вставка;
3) `catch (DbUpdateException ex) when (ex.IsUniqueViolation())` — гонку двух
   одновременных запросов ловит УНИКАЛЬНЫЙ ИНДЕКС, а catch переводит отказ
   базы на язык бизнеса. Фильтр по `PostgresException.SqlState == "23505"`
   обязателен: DbUpdateException — это «любая ошибка сохранения», глотать всё
   подряд = прятать настоящие ошибки.
Внутри catch: `ChangeTracker.Clear()` (в контексте висит несохранённая
сущность!) + перечитывание конкурента.

**Мантра**: проверка — оптимизация, констрейнт + catch — гарантия.

**Дубль ≠ конфликт**: тот же id с теми же данными → 200 «уже есть» (ретрай
клиента сработал); тот же id с ДРУГИМИ данными (другой profit / другой
владелец) → 409 ConflictException — это не ретрай, а расхождение данных.

### 3.5 Дерево: parent-pointer + рекурсивные CTE

**Хранение**: users.ParentId (self-FK, Restrict) — самый простой способ.
Closure table / materialized path / ltree отвергнуты: при глубине ≤ 10 их
цена записи не окупается.

**Обходы — WITH RECURSIVE, механика подробно** (UserTreeQueries):

```sql
WITH RECURSIVE up AS (
    -- ЯКОРЬ: выполняется один раз, даёт стартовый набор строк.
    -- Здесь: родитель стартового пользователя, Level = 1
    SELECT p."Id", p."ExternalId", p."ParentId", 1 AS "Level"
    FROM users u JOIN users p ON p."Id" = u."ParentId"
    WHERE u."Id" = {userId}

    UNION ALL

    -- РЕКУРСИВНАЯ ЧАСТЬ: выполняется ИТЕРАТИВНО. На каждой итерации `up` —
    -- это строки, добавленные ПРЕДЫДУЩЕЙ итерацией (не все накопленные!).
    -- Джойним их родителей, Level растёт. Итерации идут, пока очередная
    -- не вернёт 0 строк.
    SELECT p."Id", p."ExternalId", p."ParentId", up."Level" + 1
    FROM up JOIN users p ON p."Id" = up."ParentId"
    WHERE up."Level" < {maxDepth}      -- ГРАНИЦА: без неё цикл в данных
)                                      -- крутился бы вечно
SELECT ... FROM up ORDER BY "Level"
```

Ключевые детали:
- **Один round-trip в БД** вместо запроса-на-узел (N+1) или
  запроса-на-уровень (BFS). Вся итерация — на стороне Postgres.
- **`Level < maxDepth`** — двойная роль: бизнес-лимит И страховка от
  бесконечной рекурсии на повреждённых данных.
- **Кавычки вокруг "Id"/"Level"** — EF создал колонки в PascalCase, без
  кавычек Postgres свернёт имена в lowercase и не найдёт их.
- **Интерполяция `{userId}` в EF SqlQuery** — это FormattableString →
  ПАРАМЕТРИЗАЦИЯ, не конкатенация. Инъекции нет.
- Обход вниз — зеркальный (JOIN по ParentId = предыдущий уровень);
  GetSubtreeHeightAsync — тот же обход вниз + `MAX(Level)` (алиас "Value" —
  конвенция EF для скалярного SqlQuery<int>).
- Дерево-ответ собирается в памяти из плоского списка через
  `ToLookup(ParentId)` + рекурсивный BuildChildren — ноль дополнительных
  запросов.

**Лестница подходов к иерархиям (для собеса)**: N+1 (антипаттерн) → BFS по
уровням (запрос на уровень, хорош при жёстком лимите глубины) → рекурсивная
CTE (один запрос, канон) → смена модели хранения (materialized path/ltree,
closure table, nested sets — когда деревья огромные и читаются постоянно;
платят записью).

### 3.6 Инварианты связи: PartnerLinkRules + advisory lock

**Правила — чистая статика** (тестируется без моков): self → цикл → глубина.

**Формула глубины С УЧЁТОМ ПОДДЕРЕВА**:
`предки(партнёра) + 1 + высота_поддерева(пользователя) ≤ maxDepth`.
Смысл: самый глубокий ПОТОМОК переносимого пользователя тоже должен остаться
в лимите. Проверка только пути вверх — дыра (находка ревью №2: узел с
потомками, прицепленный к 9-му уровню, давал потомкам цепочку 14).
**Off-by-one**: сравнение строгое (`>`), уровень ровно maxDepth ДОСТИЖИМ.
Трюк: предки/высота запрашиваются с лимитом maxDepth+1 — если реальная
цепочка глубже лимита, счётчик упрётся в maxDepth+1 и формула гарантированно
даст отказ (даже если цикл в повреждённых данных «спрятался» глубже —
отказ будет, просто с формулировкой depth, а не cycle).

**Конкурентность — pg_advisory_xact_lock**. Без него два одновременных
запроса A→B и B→A проходят проверки по данным друг друга ДО коммитов и
создают цикл. Механика:
- транзакция → `SELECT pg_advisory_xact_lock(KEY)` — ЖДЁТ (не try),
  отпускается АВТОМАТИЧЕСКИ на commit/rollback (в т.ч. при исключении —
  `await using` транзакции диспозит её без коммита = rollback = лок снят);
- пользователи ПЕРЕЧИТЫВАЮТСЯ ПОСЛЕ захвата — видят коммит конкурента;
- KEY — произвольный bigint, «имя» лока по договорённости; пространство
  ключей — ОДНО НА БАЗУ (у сервисов разные базы → сервисы не пересекаются);
- один лок на все изменения дерева — грубо, но правки редки, корректность
  дороже. `ExecutionStrategy` вокруг — обязателен из-за EnableRetryOnFailure
  (EF запрещает ручные транзакции без неё); `ChangeTracker.Clear()` в начале
  блока — гигиена повтора стратегии.
- Самоссылка проверяется строками ДО транзакции (это ещё и убивало баг
  «объединённый запрос по двум равным id вернул одну строку → user стал
  партнёром сам себе»). Self не зависит от состояния БД → 400
  (ValidationException); цикл/глубина зависят → 409 (ConflictException).

**Удаление связи БЕЗ лока — осознанно**: снятие ParentId только укорачивает
цепочки, ни цикл, ни превышение глубины создать невозможно.

### 3.7 Wallets: пометка вместо удаления (критичный урок)

**WalletEntry: PK = CommissionId, строки НИКОГДА не удаляются** — Pending →
Paid (+PaidAtUtc). Почему это принципиально: PK — пожизненный ключ
идемпотентности получателя. История бага (ревью первого референса, находка
№1): выплаченные строки УДАЛЯЛИСЬ → поздний дубль доставки (штатный при
at-least-once!) проходил проверку «нет такой» → комиссия вставлялась и
выплачивалась ВТОРОЙ раз. **Правило: ключ идемпотентности живёт столько,
сколько возможны дубли — то есть вечно.**

Приём: проверка по PK (+ сравнение данных: другие Amount/владелец → 409) +
catch(23505) на гонку. Payout: entries → Paid + Balance += total одним
SaveChanges (= одна транзакция: частичных состояний нет, рестарт посреди —
безопасен).

**paymentStatus в детализации — синхронный запрос к Wallets** (payments:query)
с деградацией: Wallets лёг → статус Unknown, а не 500. Альтернатива —
обратное сообщение CommissionsPaid → is_paid в Commissions (event-driven,
без запроса на чтении); выбран запрос ради простоты: меньше движущихся
частей, честная деградация. Trade-off: чтение детализации зависит от
доступности Wallets (смягчено Unknown).

### 3.8 Фоновые джобы: PollingBackgroundService + try-lock

Базовый класс (Shared) инкапсулирует все три железных правила фоновика:
1) вечный цикл на PeriodicTimer до CancellationToken;
2) try/catch ВНУТРИ тика (исключение из ExecuteAsync убивает весь хост);
3) scope на единицу работы (BackgroundService — синглтон, DbContext — scoped).

Плюс **advisory TRY-lock на тик** (`pg_try_advisory_lock`, у каждого джоба
свой LockKey): взял — работаешь, не взял — «другой экземпляр работает»,
пропуск тика. Следствие: при N экземплярах сервиса активен ОДИН экземпляр
каждого джоба → нет ни двойной обработки, ни двойной выплаты, ни гонок.
Это замена SKIP LOCKED-клейму: проще, для этого масштаба достаточно;
SKIP LOCKED (конкурентная обработка пачек несколькими экземплярами) — план
развития, если один воркер перестанет успевать.

**Гонка, которую лок закрывает в payout** (уметь рассказать): экземпляр B
читает Pending-строки ДО коммита A (видит E1), а кошелёк — ПОСЛЕ (баланс уже
+E1) → пишет balance + E1 повторно. Read committed: каждый запрос видит
свежие коммиты, между двумя чтениями мир меняется.

Опции джобов (интервалы) — через именованные Options из конфигурации
(`AddPollingJob<T>` биндит секцию по имени класса).

### 3.9 Ретраи — три этажа

1. **БД**: `EnableRetryOnFailure` — EF сам повторяет транзиентные сбои команд.
   Цена: ручные транзакции только через ExecutionStrategy.
2. **HTTP**: `AddStandardResilienceHandler` (Polly v8) — конвейер
   rate limiter → total timeout → retry (экспоненциальный backoff) →
   **circuit breaker** → attempt timeout. Предохранитель: closed (норма) →
   open (порог ошибок превышен: вызовы падают МГНОВЕННО — не копим висящие
   потоки, не добиваем лежащего соседа) → half-open (пробный вызов). Retry
   защищает операцию, breaker — систему.
3. **Персистентный** (переживает рестарт): Attempts + NextAttemptAtUtc +
   LastError на событиях и outbox-строках; backoff 2^attempts с потолком
   (~300с). Упавший тик = отложенный повтор, не потеря.

**Unresolved** — отдельный статус для «пользователь не найден»: событие могло
прийти РАНЬШЕ регистрации владельца (каналы не упорядочены между собой).
Похоронить как Processed = потерять комиссии навсегда (находка ревью №6).
Повтор по NextAttemptAtUtc; лимит попыток — в Limitations.

### 3.10 Graceful shutdown — цепочка

docker stop → SIGTERM → доходит до dotnet только при **exec-форме
ENTRYPOINT** (`["dotnet","X.dll"]`; строковая форма спрятала бы процесс за
sh) → HostOptions.ShutdownTimeout (10с в ServiceDefaults) → Kestrel
дорабатывает запросы, PeriodicTimer-циклы выходят по токену →
compose stop_grace_period (35с) — СНАРУЖИ БОЛЬШЕ, ЧЕМ ВНУТРИ, иначе SIGKILL
посреди уборки. Финальная страховка: даже грязный обрыв безопасен —
транзакции откатились, статусы/outbox не помечены → повтор после старта
(дивиденд идемпотентности).

### 3.11 Наблюдаемость

- **Метрики**: prometheus-net, UseHttpMetrics + MapMetrics; бизнес-счётчики
  с ЛЕЙБЛАМИ результата (users_created{result=created|duplicate},
  partner_links{result=linked|cycle|...}, profit_events_received{...}) —
  один счётчик отвечает и «сколько», и «как именно». Префикс
  partnercommission_. Prometheus-контейнер в compose скрейпит всех.
- **Логи**: stdout (докер собирает), SimpleConsole + IncludeScopes;
  ActivityTrackingOptions (TraceId/SpanId/ParentId) — W3C trace context
  прокидывается HttpClient'ом автоматически → один TraceId в логах всех
  сервисов без Serilog и ручного correlation id. BeginScope в хендлерах
  добавляет бизнес-ключи (EventExternalId и т.п.).
- **Health**: /health/live (Predicate = _ => false — НОЛЬ внешних проверок:
  live с проверкой БД заставил бы оркестратор рестартить здоровый под из-за
  мигнувшей базы) и /health/ready (тег ready: Npgsql). Compose-healthcheck
  сервисов — curl на ready (curl доустановлен в runtime-образ!);
  depends_on: service_healthy = порядок ПЕРВОГО старта, живучесть в рантайме
  — ретраи в приложении.

### 3.12 Ошибки → HTTP: IExceptionHandler + ProblemDetails

Один ApiExceptionHandler (Shared, FrameworkReference на ASP.NET) со
switch'ем: NotFoundException→404, ConflictException→409,
ValidationException→400; незнакомое → return false → дефолтный механизм
AddProblemDetails отдаёт стерильный 500 БЕЗ стектрейса (утечка internals —
уязвимость). Формат — ProblemDetails (RFC 9457): единый с ошибками
валидации [ApiController], traceId в теле автоматически.
Дисциплина: switch хендлера и набор бросаемых типов — два списка,
синхронизируемые только вручную; новый тип исключения → проверить хендлер.
Правило исключения-vs-результат: исключения — для ОТКАЗОВ, прерывающих
операцию (не найден, конфликт); результаты — для ветвлений УСПЕХА
(created/duplicate — оба успех).

### 3.13 Данные: ключи, деньги, сид

- **PK**: User — суррогатный Guid (владеемая сущность с self-FK: стабильность
  ключа, компактный FK, id генерится в коде до вставки — нужно outbox'у);
  Wallet/WalletEntry — естественные ключи (UserExternalId / CommissionId):
  проекции из сообщений, внутренних ссылок нет. Критерий: владение данными
  и наличие ссылок, не единый стиль. Наружу Guid не светится — внешний мир
  говорит на ExternalId.
- **Деньги**: только decimal / numeric(18,4); Fibonacci — предвычисленная
  таблица F(1)=1, F(2)=1 (допущение, ряд в задании не определён);
  округление banker's (ToEven) до 4 знаков.
- **Enum'ы в БД**: SchemaType — строкой (HasConversion<string>): историческая
  запись, которую читают глазами при разборах; Status — int'ом: служебный
  фильтр. Явные числа у enum-статусов — защита от сдвига значений при
  вставке нового члена.
- **Сид настроек — идемпотентный сидер на старте, НЕ HasData**: HasData
  «поддерживает» данные и будущая миграция могла бы UpdateData'ой сбросить
  переключённую админом схему. Правило: HasData — для неизменяемых
  справочников; runtime-изменяемое — только «insert if missing».
- **Миграции — Migrate() на старте ПОД advisory-локом** (MigrateWithLockAsync):
  N экземпляров стартуют одновременно — мигрирует один. В проде миграции —
  шаг пайплайна (оговорено в README).

### 3.14 Docker

- **Dockerfile**: multi-stage (sdk ~800МБ собирает → aspnet ~220МБ только
  рантайм: размер + поверхность атаки); порядок COPY = кеш слоёв (csproj
  всех проектов-зависимостей + restore ДО исходников: правка кода не
  перезапускает restore); .dockerignore (bin/obj/.git) иначе контекст
  гигантский; USER app (non-root); curl доустановлен ради compose-healthcheck.
- **Compose**: YAML-якоря (x-service-defaults) убирают дублирование; сеть —
  встроенный DNS (адреса = имена сервисов, `localhost` внутри контейнера —
  сам контейнер!); внутри все слушают 8080 (свой namespace у каждого), наружу
  8081-8083; постгрес на **5433** (5432 занят dev-контейнером pc-postgres —
  реальный конфликт, пойманный на практике); init-скрипт трёх баз
  выполняется ТОЛЬКО при первой инициализации тома (правки → down -v);
  именованный том переживает down (повторный прогон сценария → конфликты
  идемпотентности; чистый прогон — down -v).

## 4. Таблица идемпотентности (все швы)

| Шов | Механизм |
|---|---|
| Повторный POST user/event | UNIQUE по ExternalId + check/catch(23505) → «дубль» как успех |
| Дубль с другими данными | сравнение полей → 409 |

| Потеря при доставке | outbox в транзакции с данными; пометка после успеха |
| Конкурентные правки дерева | pg_advisory_xact_lock + перечитывание после захвата |
| Одновременный старт N экземпляров | Migrate под локом |

## 5. Масштабирование (как есть и куда расти)

**Сейчас**: API stateless — экземпляры множатся свободно (идемпотентный
приём выдерживает ретраи на разные экземпляры; правки дерева сериализованы
локом). Джобы: один активный на джоб через try-lock — корректно при любом N.
Ограничение: пропускная способность фоновой обработки = один воркер.

**Лестница развития** (каждый шаг — по сигналу, не впрок):
1. Вынос воркеров в отдельные процессы (hosted services переезжают
   механически; автоскейл по глубине очереди из метрик).
2. Брокер вместо HTTP-доставки (outbox — готовая точка замены; Kafka даёт
   fan-out, replay, партиции с ordering по userId — что заодно решает
   конкурентную обработку красивее SKIP LOCKED).
3. SKIP LOCKED-клейм, если нужен конкурентный процессинг до брокера.
4. Данные: read-реплики (списки/балансы) → партиционирование
   profit_events/commissions по дате → шардирование по UserExternalId
   (естественный ключ: всё в системе секционируется по пользователю).
5. Redis-кеш цепочек предков (горячий путь расчёта; инвалидация по
   изменению связи).

**Ключевая фраза**: каждый шаг — замена транспорта или вынос готового
компонента, не переписывание логики: надёжность живёт в коде и данных
(идемпотентность, outbox, статусы), а не в инфраструктуре.

## 6. Осознанные ограничения (и почему это ок)

- HTTP+outbox вместо брокера — прямое допущение задания; точка замены готова.
- Один Postgres-инстанс / три базы — изоляция логическая полная, граница
  проведена; в проде — отдельные инстансы.
- Shared с исключениями/хостингом — cross-cutting минимум против трёхкратного
  дублирования; жёсткая граница: бизнес-логики и сущностей там не бывает.
- Нет auth (в т.ч. /internal, /admin) — вне скоупа; в проде gateway + s2s.
- Payout-интервал в секундах — наблюдаемость демо; в проде часы/расписание.
- Unresolved ретраится без лимита — в проде предел попыток + алерт.
- Миграции на старте — удобство «одной команды»; в проде — пайплайн.
- paymentStatus через sync-запрос — простота + деградация Unknown;
  альтернатива (backflow-сообщение) описана.

## 7. Хронология уроков (чтобы помнить, откуда шрамы)

1. Удаление ключа идемпотентности после выплаты → двойная выплата (v1
   референса). → «ключ живёт вечно».
2. Глубина без учёта поддерева + off-by-one (уровень 10 недостижим). →
   формула с subtree, строгое `>`.
3. Гонка A→B/B→A → цикл. → xact-лок + перечитывание.
4. Схема при расчёте → недетерминизм. → штамп при приёме.
5. Unresolved = Processed → потерянные комиссии. → статус + повтор.
6. Общий DbContext на батч → упавшее событие травит остальные. → scope на
   единицу работы.
7. HasData для runtime-настройки → мина UpdateData. → сидер if-missing.
8. `[property:]` на позиционном record'е → MVC бросает
   InvalidOperationException; атрибуты — на ПАРАМЕТРАХ. (В финале minimal
   контрактов нет — контроллеры, но правило помнить.)
9. Metrics — требование задания, а не опция (пропущены в v1).
10. Том compose переживает down → «грязные» повторные прогоны (я сам поймал
    409 на «первом» событии). → down -v для чистого прогона.
